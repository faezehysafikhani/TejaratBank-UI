# پرامپت تست کامل دسترسی‌ها (سمت، پست، سوییچ پست)

> این متن را کامل برای Claude extension (Chrome) بفرست. تست‌ها روی **بیلد لوکال** است. کد را تغییر نده؛ فقط تست کن و گزارش بده.

---

## نقش تو
تو تستر QA هستی. سامانه‌ی مدیریت فعالیت‌ها (فرانت: React/Vite، بک‌اند: NexusCore) را روی بیلد لوکال اجرا کن و **همه‌ی بخش‌هایی که با دسترسی (Permission) کار می‌کنند** را در سناریوهای زیر تست کن. هر سناریو را هم از **رابط کاربری** و هم از **API** (Network tab یا `fetch`/`curl` با توکن همان کاربر) بررسی کن؛ سمت سرور مرجع است، رابط فقط باید با آن هم‌خوان باشد.

## قواعد
- هیچ فایلی را تغییر نده و commit نکن. فقط تست و گزارش.
- برای هر مورد: **شناسه، مراحل، نتیجه‌ی مورد انتظار، نتیجه‌ی واقعی، قبول/رد، شواهد** (متن پاسخ API، کد وضعیت، عکس صفحه). قبول بدون شاهد حساب نمی‌شود.
- هر خطای کنسول، پاسخ ۴xx/۵xx غیرمنتظره، یا ناهماهنگی رابط و سرور را جدا ثبت کن.
- اگر مرحله‌ای قابل اجرا نبود، دلیلش را بنویس و ادامه بده. حدس نزن.
- در پایان: جدول خلاصه (تعداد قبول/رد/اجرانشده) و فهرست باگ‌ها به ترتیب شدت.

## ۰) آماده‌سازی
1. فرانت و بک‌اند را لوکال بالا بیاور (دستورها در `README.md` و `DEPLOYMENT-CONFIG.md`). نسخه‌ی NexusCore باید از برنچ `feature/1405-08-07-orgNode` ساخته شده باشد.
2. **شرط اول (P0):** کاربری که دو پست دارد بساز (بخش ۱). با توکن او `GET /api/identity/auth/me` را یک بار بدون هدر و یک بار با هدر `X-Active-Posts: <شناسه‌ی یکی از پست‌هایش>` بزن. اگر لیست `permissions` فرق نکرد، بک‌اند قدیمی است؛ **همین‌جا متوقف شو** و گزارش بده.
3. حساب‌ها:
   - `ADMIN`: نقش Administrator.
   - `U0`: بدون نقش، بدون گروه، بدون دسترسی مستقیم، بدون پست.
   - `UV`: فقط «مشاهده ساختار سازمانی» (`org_structure.view`).
   - `UM`: فقط `org_structure.manage_position_permissions` (و پیش‌نیازهایش).
   - `UA`، `UB`: هر کدام دو پست دارند (بخش ۱).
4. داده‌ی سازمانی: ۲ شرکت (C1, C2)، چند معاونت/واحد، سمت‌های `P1`..`P4` (هر سمت برای هر دو شرکت)، چند پست در هر واحد.

## ۱) ساخت پیکربندی نمونه
- سمت `P1` در C1: فقط `Notes.Manage` و `Tasks.View`.
- سمت `P2` در C1: فقط `Tasks.View` و `Tasks.Create`.
- پست `X` (از سمت P1) را هم دسترسی `Meetings.View` بده.
- `UA` را همزمان به پست از P1 و پست از P2 (هر دو C1) بگمار. `UB` را به پستی از P1 در C1 و پستی از P1 در C2.
- `U0` را فقط یک پست بدون هیچ دسترسی بده (سمت `P3` خالی).

## ۹) ماتریس بخش‌ها (برای هر ردیف: بدون دسترسی / با دسترسی، رابط + API)
برای هر بخش دو کاربر یا دو حالت بساز و نتیجه را در رابط **و** API چک کن:

- **فعالیت‌ها:** `Tasks.View` (کانبان، تقویم، گزارش‌ها)، `Tasks.Create`، `Tasks.Edit`، `Tasks.Delete`، `Tasks.Comment`، `Tasks.UploadFiles`، `Tasks.ManageAll` (دیدن همه‌ی فعالیت‌ها؛ بدون آن فقط فعالیت‌های خود/دسترسی‌دار).
- **جلسه‌ها:** `Meetings.View/Create/Edit/Delete`، `Meetings.InviteHigher`، `Meetings.AccessAllPeople`.
- **یادداشت شخصی:** `Notes.Manage` (تب، ایجاد/ویرایش/حذف، API یادداشت‌ها).
- **گزارش‌ها:** تب با `Tasks.View` یا `Meetings.View` یا `users.view`؛ گزارش کاربران فقط با `users.view`.
- **کاربران:** `users.view/create/update/change_status/delete/assign_roles/assign_permissions`؛ ویرایش دسترسی شخصی طبق `PERSON_ACCESS_UI_ENABLED` مخفی است (بررسی کن مخفی بماند).
- **نقش‌ها:** `roles.view/create/update/assign_permissions`.
- **تنظیمات سامانه:** `settings.view/update`، پیامک (`sms_settings.*`)، LDAP (`ldap_settings.*`)، SSO (`sso_settings.view`)، لاگ حسابرسی (`audit_logs.view`)، نشست‌ها (`sessions.view/revoke/revoke_all`).
- **ساختار سازمانی:** `org_structure.view/manage_companies/manage_positions/manage_assignments/manage_position_permissions`، `org_structure.node.*`، `manage_rules`، `manage_templates`، `team_members_any_unit`، `assign_tasks_any_level`، `manage_substitution` (کارتابل جانشینی)، `all_companies`.
- **تیم کاری/گروه‌ها و چت:** دسترسی‌های گروه، ساخت تیم، چت.
- **ماژول‌های دیگر (اگر در منو هستند):** پروژه‌ها، استراتژی، دانش، تیکتینگ، KPI و ... به همان روش.

برای هر دسترسی: (۱) بدون آن، منو/دکمه نیست و API ۴۰۳ می‌دهد؛ (۲) با آن، همه‌چیز کار می‌کند؛ (۳) پیش‌نیازهایش خودکار می‌آید؛ (۴) وقتی از سمت داده شد و بعد برداشته شد، دقیقاً مثل (۱) می‌شود.

## ۱۰) چند منبع دسترسی با هم
| ID | سناریو | انتظار |
|---|---|---|
| H1 | همان دسترسی از نقش + سمت | برداشتن از سمت اثری نکند (هنوز از نقش) |
| H2 | از گروه + پست | برداشتن یکی دیگری را حفظ کند |
| H3 | منع صریح (denied) برای کاربر | بر همه‌ی منابع، از جمله پست، غالب شود |
| H4 | صفحه‌ی دسترسی کاربر (ادمین) | نشان «از سمت/پست» با نام درست؛ دسترسی پست در همان صفحه تغییر داده نشود |
| H5 | ادمین صفحه‌ی دسترسی کاربر دیگر را ببیند | محاسبه با سوییچ ادمین **اثر نگیرد** (هدر فقط برای خود کاربر) |

## ۱۳) ناهماهنگی رابط و سرور (قانون عمومی)
در همه‌ی سناریوها: هر جا رابط چیزی را نشان می‌دهد که API رد می‌کند (یا برعکس) یک باگ مستقل است. این‌ها را به‌صورت جدا لیست کن.

## ۱۴) خروجی نهایی
1. جدول نتایج (ID، قبول/رد/اجرانشده، شواهد).
2. فهرست باگ‌ها: عنوان، مراحل بازتولید، انتظار/واقعیت، شدت.
3. فهرست بخش‌های وابسته به دسترسی که در UI پیدا کردی و در این سناریو نبود.
4. تعداد درخواست‌ها و خطاهای کنسول در سناریوی سوییچ سریع (G8).
